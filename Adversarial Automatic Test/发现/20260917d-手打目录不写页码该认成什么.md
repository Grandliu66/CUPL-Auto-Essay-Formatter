# 发现 2026-09-17-4：手打目录"不写页码"那种，工具该认成什么？

> 用户追问（原话）：
> 「按引言来定是个办法，但是，可能连引言也没有。**你认为在工具里这种情况……都认成正文标题比较合适，吗？**」
> 「而且引言当范围好像是正式代码里没有的，你不能单 AAT 里补，对吧？」

## 一、先摆证据（`_probe_nopage_toc.py`，夹具＝用户给的那份）

夹具 `_fixtures/手打目录无页码.docx`（原样照抄用户的例子）：

```
目录 / 一、111 / 二、222 / 引言 / xxx / 一、111 / 1111111 / 二、222 / 2222222
```

工具实际干了两件事：

1. **告警：一条都没有。**（`pipeline.review()` 的收集器是空的）
2. **成品**（段号含自动补齐的部件）：

| 段 | 文字 | 结果 |
|---|---|---|
| 14 | `一、111` | **一级标题**（这是目录条目） |
| 15 | `二、222` | **一级标题**（这是目录条目） |
| 16 | `引言` | 一级标题（锚点，正常） |
| 17 | `xxx` | 正文 |
| 18 | `一、111` | 一级标题（真标题） |
| 20 | `二、222` | 一级标题（真标题） |

⇒ 4 个"一级标题"里 2 个是假的，**而且没有任何提示**。用户唯一的线索是结构页里目录块下面多出两行一级标题。

> 顺带记一个观察（不在本轮范围）：序号的跳号/重号告警**没有覆盖引言之前的那两段**（这里是 一、二、一、二 回退，本该报"跳号"）。要不要查、要不要覆盖，另说。

## 二、我的判断：**不改，维持“认成正文标题”**

四条理由：

1. **触发概率差得远**：“手打目录且**不写页码**”是很少见的写法（目录的用处就是给页码）；而“目录后不写引言、直接从 `一、` 开始写正文”在课程论文里很常见。
2. **误伤代价不对称**：把真标题吞成“多余的正文”，用户会收到 A8 告警“多余的正文：请检查目录下疑似多余的正文”——但用户看到这句话，很难联想到“那其实是我的第一章标题”，多半会顺手把它改成正文；反过来，目录条目被当成标题，用户一眼就能在结构页/目录里看出不对。
3. **“范围法”本身建立在一个不牢的假设上**：它假设“目录标签后面紧跟的连续标题行一定是条目”，而这个假设在最需要它的场景（没有引言等部件做界的文档）恰恰最不成立——那种文档往往就是“目录后面直接写正文”。
4. **判错了谁负责**：见第三节，这一条得表与正式代码一起改，不是 AAT 能单独定的。

### 如果一定要做，有个比“范围法”更硬一点的信号

目录条目是正文标题的**抄本** ⇒ “这一段与文档后面某一段的文字完全相同”。用户给的例子里 `一、111`/`二、222` 各出现两次，这个信号能抓住。

但它有自己的误伤面：**二/三/四级标题重名很常见**（不同章里都有“（一）基本概念”），那种“第一处”会被当成抄本而被吞。要用就得限制在“一级标题 + 与更靠后的段完全相同 + 落在目录标签附近”这类窄条件里。**未裁决，未实现。**

## 三、用户的第二个问题：**对，不能单在 AAT 里补**

* AAT 的预估只做一件事：**按表算“应该是什么”**。表里写一条产品没实现的规则 ⇒ AAT 只会**长期报同一处分歧**（一张挂在墙上的“待实现清单”）。这类分歧对“发现新 bug”没有价值，还会淹没真正的信号。
* 而且“范围法”是**识别逻辑变更**，动的是产品行为，得走正规路径：**用户拍板 → 写进表 → 正式代码实现 → AAT 按表验证**。
* **这次的“页码尾巴”那条不属于这种情况**：正式代码里本来就有（`detect.hand_typed_toc_entries()`，2026-09-15 用户裁决的压测观察项 O10）。我这次只是把**表**补上、让表与代码对齐，并把表里那句话**收紧到与代码同宽**（紧跟标签 + 页码链断就停 + 碰到下一个部件停），否则我的预估会比产品宽，凭空造出假分歧。

## 四、顺带说明：这类问题**差分看不见**

`_rerun_all.py` 在那份（旧的 9 段）夹具上报的差异是 段0（题目占位文本的去留）与 段17（`xxx` 被我的预估当成了题目）——都是残缺夹具本身引起的，**段1/段2 一处都没报**：因为我的预估和引擎**都**把它们认成了一级标题。两边一致地错 ⇒ 差分为零。

⇒ 所以第五节的裁决**不能靠差分来验证**，得写断言（见 `_check_toc_boundary.py`）。

## 五、用户裁决（同日）：**允许将引言作为边界**，三处都得改

用户原话：「你去直接在正式代码里允许将引言作为边界，然后编辑表，然后实现AAT。另一个目前没在工作。」

### 实现的解读（保守那一档，与原文不完全确定的地方）

「引言当边界」落实成：**标题形状的行要不要算手打条目，得先确认标签后面能一路走到「引言」**。

为什么加这个前置条件：用户前面自己说了「可能连引言也没有」。若只要“像标题”就算，那么
**“目录标签后面直接写正文标题”（没有引言）会被误伤**——那是真实写法，而且现有的
`tools/_check_hand_typed_toc.py` 第 ③ 例就是在钉这一条。加了这个条件之后：

* 用户给的例子（`目录 / 一、111 / 二、222 / 引言`）⇒ 那两行被放过 ✓
* `目录 + 一个真标题`（无引言）⇒ 仍旧是标题，**不误伤** ✓
* 若有引言、但链中间断了（目录页里多写了正文）⇒ 断开处之后的真标题也不受影响 ✓

> 如果用户的本意是“没引言时也要放宽”，说一声即可改——那会把上面第 ② 条代价吃进去。
